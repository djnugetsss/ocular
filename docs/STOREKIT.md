# StoreKit 2 — Ocular Pro

> **Superseded (2026-07-24).** Subscriptions now run through **RevenueCat** —
> see [REVENUECAT.md](./REVENUECAT.md). The JS entitlement layer talks to
> `react-native-purchases`, not the native `ocular-store` module described
> below. The Swift module is kept in the repo for reference and as a fallback,
> but it is no longer on the entitlement path, and nothing in `src/` imports it.
> This document is retained for its App Store Connect / product-configuration
> checklist, which still applies.

How subscriptions were wired under the native StoreKit module, and the checklist
to ship them.

## Architecture

```
modules/ocular-store/            Native module (Swift, StoreKit 2)
├── ios/StoreKitBridge.swift        Pure StoreKit — no Expo/React. The engine.
├── ios/OcularStorePayload.swift    The one place wire payloads are built.
├── ios/OcularStoreModule.swift     Expo glue: promises, events, the observer.
└── src/OcularStore.types.ts        The TS contract (mirrors the payload file).

src/features/subscription/
├── products.ts                  The only home of the product ids.
├── store-kit.ts                 Null-safe adapter + `tierFromEntitlement`.
├── entitlement-cache.ts         Per-user offline cache of the last verified tier.
├── entitlement-source.ts        Resolution precedence, purchase/restore policy.
├── subscription-provider.tsx    Startup verify, live observer, purchase/restore.
├── use-products.ts              Live localized prices (static USD as a floor).
└── entitlements.ts              What each tier grants. No StoreKit types here.
```

**The boundary that matters:** `StoreKitBridge.swift` has no reference to Expo,
React, or any bridge type — the same rule `FaceTrackingSession` follows for the
Vision pipeline (PLAN.md §4). Everything a screen sees is the resolved
`Entitlements` shape; no `if (productId === …)` and no StoreKit type ever
reaches a component.

**Security invariants** (each has a test):

- Only `.verified` transactions grant anything. `.unverified` is dropped and
  never finished, so a later legitimate verification can still deliver it.
- Entitlement is decided offline from StoreKit's local signed cache; renewal
  metadata (network) is enrichment only and never downgrades a subscriber.
- An active entitlement for a product this build does not sell collapses to
  **free** — a stale receipt for a discontinued product cannot unlock the app.
- Entitlement is **never** a `profiles` column: a client-settable `is_pro`
  would be bypassable with the anon key that ships in the binary.

## What each failure does

| Situation                   | Behavior                                                                 |
| --------------------------- | ------------------------------------------------------------------------ |
| Offline at launch           | StoreKit's signed cache answers; JS cache covers a missing native module |
| Cancelled purchase          | Silent — nothing changed, no nag                                         |
| Failed purchase             | Toast; network failures worded distinctly. Nothing charged               |
| Pending (Ask to Buy / SCA)  | "Pending approval" toast; the observer adopts it if it clears            |
| Revoked / refunded          | Observer pushes the change; access ends without a relaunch               |
| Renewal                     | Observer adopts it live; cache refreshed for the next launch             |
| No StoreKit (Expo Go / web) | `isStoreAvailable()` false; dev builds simulate, prod says so            |

## Local testing (Simulator, no App Store Connect)

1. `Ocular.storekit` (repo root) defines both products for local testing.
2. In Xcode: **Product → Scheme → Edit Scheme → Run → Options → StoreKit
   Configuration → `Ocular.storekit`**. (The `ios/` folder is git-ignored and
   regenerated by prebuild, so this is set on the local scheme, not committed.)
3. Run on a Simulator. The paywall shows the configuration's prices; purchase,
   restore, and Manage Subscriptions all work against the local store.
4. Editor → the `.storekit` file lets you force renewals, refunds, and billing
   retry to exercise the observer paths.

The dev/preview **Simulated plan** switch in Profile → Plan still works with no
`.storekit` at all (Expo Go, bare Simulator) — a real purchase clears it.

## Deployment checklist

### App Store Connect — before any TestFlight build

- [ ] **Paid Apps agreement** active (Business → Agreements). Products do not
      load until it is, and this is the single most common "prices are blank"
      cause.
- [ ] Create the **auto-renewable subscription group** "Ocular Pro".
- [ ] Create product **`ocular.monthly`** — $3.99/month. Product ID must match
      `PRODUCT_IDS.pro_monthly` exactly.
- [ ] Create product **`ocular.yearly`** — $39.99/year. Must match
      `PRODUCT_IDS.pro_annual`.
- [ ] Each product: localized display name + description, price, and a
      **review screenshot** of the paywall (required, or the product is stuck
      "Missing Metadata").
- [ ] Subscription group **localization** and an **App Store promotional**
      review note describing the free-vs-Pro split.

### Xcode / project config

- [ ] Add the **In-App Purchase** capability to the app target (adds the
      StoreKit entitlement). In this Expo project, add it via an
      `expo-build-properties`/entitlements config so `prebuild` reproduces it —
      do **not** hand-edit `ios/` (it is regenerated).
- [ ] Confirm deployment target ≥ **16.4** (already set; StoreKit 2 needs 15+).
- [ ] Production/Release scheme has **no** StoreKit configuration file attached
      (that flag is for local testing only; shipping with it points the app at
      a fake store).
- [ ] `pod install` shows `OcularStore` integrated; autolinking resolves
      `OcularStoreModule` (`npx expo-modules-autolinking search`).

### Sandbox testing (real StoreKit, pre-production)

- [ ] Create a **Sandbox Apple Account** (App Store Connect → Users and Access
      → Sandbox).
- [ ] On device: Settings → App Store → sign the sandbox account into the
      **Sandbox** slot (not the main account).
- [ ] Verify **purchase** → Pro unlocks, gates reopen without relaunch.
- [ ] Verify **restore** on a fresh install of the same sandbox account.
- [ ] Verify **cancel** (dismiss the sheet) leaves Free, no error.
- [ ] Verify **Ask to Buy** (sandbox family) surfaces the pending state, and
      that approving it later flips to Pro via the observer.
- [ ] Verify **revocation/refund** (sandbox subscription management) drops the
      user to Free live.
- [ ] Verify **airplane mode at launch** keeps a subscriber on Pro (offline
      cache), and that a first-ever launch offline does not falsely grant Pro.
- [ ] Confirm the plan row shows **"(Sandbox)"** so testers never mistake a
      sandbox sub for production.

### App Review

- [ ] "Restore Purchases" is present and functional on the paywall (Guideline
      3.1.1 — required).
- [ ] Manage Subscriptions reachable (Profile → Plan → Manage subscription).
- [ ] Privacy Policy and Terms (with the auto-renew disclosure) linked from the
      paywall — already wired to `LEGAL_URLS`; confirm both pages are live.
- [ ] Auto-renew disclosure text present near the CTA ("Cancel anytime… Renews
      until you do") — already on the sheet.
- [ ] Review notes: sandbox account credentials + one line on the free-vs-Pro
      split and that all limits are presentational (no data is deleted).
- [ ] Prices shown are StoreKit's `displayPrice` (localized), never the
      hardcoded USD floor — verify on a non-US storefront if possible.

### Post-launch (deferred, not blocking)

- [ ] **Server-side receipt validation**: an edge function that checks Apple's
      API, keyed on the `appAccountToken` (the Supabase user id) the purchase
      already forwards. Until then entitlement is client-verified, which is the
      same posture as StoreKit's own on-device cache.
- [ ] **App Store Server Notifications v2** → the same edge function, so
      refunds/cancellations are known server-side even if the app never reopens.
